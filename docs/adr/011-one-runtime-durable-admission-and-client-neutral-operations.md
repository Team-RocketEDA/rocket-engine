# ADR-011: One client-blind runtime with durable admission and scoped design operations

*Status: accepted (2026-11-01) | Refines: [ADR-005](005-caller-blind-engine-client-edge-approvals.md), [ADR-009](009-parallel-batches.md) | Evidence: [vision alignment review](../work/E2E-REREVIEW/vision-alignment.md)*

## Context

RocketEDA needs one engine process accessible from the IDE frontend and the agent adapter. The engine must own the same project state, run ledger, scheduler, queue, coalescing decisions and events regardless of transport. A bounded FIFO can protect the runtime from bursts, but execution should begin as soon as capacity and dependencies allow. A response that acknowledges accepted work must mean that the request is durably recorded and cannot be silently lost.

The engine's operation vocabulary is intended to cover reusable components and subcircuits, linked schematic/layout/source/model views, geometry authoring, placement and connection, and synthesis/verification on either a unit or the full design. The Ready `CANVAS-CST` ticket defines `canvas.toml` as the TOML design-intent and tool-settings file. I28 makes its project revision, path references and resolved effective settings part of replayable run ingredients. EDA work can be expensive and parallel, so repair-loop limits need a precise meaning separate from queue throughput. Source modules must remain small enough for one responsibility to be understood and changed safely.

Current source reviewed at `ec8c923` has useful foundations but does not yet establish these full guarantees. `Engine.submit()` drains work inline before returning; the bounded pool is in memory and reports `pool_full`; coalescing is local to an Engine instance; the MCP adapter constructs its own Engine without a durable root. The [E2E invariant map](../work/E2E-REREVIEW/invariant-map.md) is a historical snapshot at `a8aaa09` and its proven labels cover narrower journeys.

## Decision

1. **One EngineRuntime owns all engine state for an IDE application.** The frontend attaches through stdio or localhost HTTP; MCP attaches through its bridge/broker. Transport bridges may run separately, but they do not create an Engine or duplicate project state, queues, ledgers, coalescers or event sequences. All adapters use the same operations, validation, scheduling, evidence and project effects. Trusted actor/session metadata may be carried for audit and harness policy; client identity does not select a different operation implementation.
2. **Submission is prompt, durable admission followed by immediate dispatch.** The runtime snapshots and durably records a valid request before acknowledging it, then dispatches immediately when capacity permits. The FIFO is a durable burst buffer and recovery mechanism. Capacity state tells both controlled clients to pause and resume. A saturation race is rejected before admission with a retryable response; accepted work is never silently dropped. Coalescing maps equivalent same-project requests with the same normalized operation, arguments and pinned input snapshot to one run, while recording every request ID. Different snapshots and explicit forced reruns remain separate. `run_job` is not a required second start signal.
3. **Operations support explicit unit and canvas scope.** Applicable operations name a component/subcircuit or project top-level target, resolve and pin its dependency closure, and report the exact target and snapshot. Unsupported target/operation pairs fail explicitly instead of silently broadening scope. A component's schematic, layout, source and models share its canonical identity and declared mappings. Layout editing uses the shared engine vocabulary for geometry mutation, with layer identity and project coordinates owned by versioned design state; GDSFactory is one downstream geometry backend, not the only authoring route. [ADR-012](012-always-editable-layer-catalog-and-process-bindings.md), as amended by [ADR-013](013-magic-aligned-technology-driven-layout.md), records the current layer and technology-profile contract.
4. **I28 governs project shape and replay.** `canvas.toml` is versioned project design truth for targets and tool knobs; contained file references resolve inside the project. Each run pins the project revision, PDK id/revision/manifest hash, deck, solver/version, seeds and resolved configuration, plus any other consumed ingredient. A replay must reproduce the same verdicts, findings and measurements and name any drifted field; native output bytes need not match. Generated configs and run outputs are exhaust, never design truth. Required defaults are resolved and recorded; a missing required value fails loudly rather than becoming a hidden input.
5. **Repair iteration is a harness repair-round budget, not a queue or job-attempt limit.** The baseline generation/run is iteration 0. A changed design after a failed required check followed by rerunning affected checks is one repair iteration; parallel checks against that same changed revision count once. Manual runs and infrastructure failures do not consume the session budget. The harness gate applies to every solver submission route, with trusted session attribution; transport choice does not create a bypass.
6. **Engine source modules stay below 3,000 lines.** Split cohesive responsibilities before reaching the limit. Existing over-limit modules are non-conforming and require decomposition; nearby modules should be split before they cross the limit.

This refines ADR-009: `pool_full` may reject work only before durable admission. It does not contradict zero loss for acknowledged work. ADR-005 remains in force: the engine is caller-blind and actor/session metadata is not an alternate authorization path.

## Alternatives considered

1. **One Engine per transport or project adapter.** Rejected because adapters could disagree on revisions, queue capacity, coalescing, run status and event order; they would not constitute one engine runtime.
2. **Acknowledge before durable admission and rely on clients to retry.** Rejected because a disconnect or restart can lose work that appeared accepted. Retry handles only unacknowledged requests; it cannot repair a false acknowledgement.
3. **Keep `submit` and `run_job` as mandatory sequential phases.** Rejected because it adds a client round trip and creates an avoidable boundary where accepted work can sit idle. A compatibility/deferred control operation may remain, but cannot be required for progress.
4. **Coalesce only by command name, or reuse a previous completed run.** Rejected because arguments, target and input revision change the work; only equivalent in-flight/admitted requests pinned to the same snapshot share execution.
5. **Make every GDSFactory method a bespoke engine operation, or store all geometry as YAML polygons.** Rejected because the existing prepared library/script route already provides the domain implementation. The engine exposes a safe, revisioned authoring boundary and can add typed high-value operations without cloning the library API.
6. **Count every solver job or retry as a repair iteration.** Rejected because parallel checks on one changed design are one repair round, while infrastructure retries do not represent agent design progress.
7. **Keep large modules together until a future rewrite.** Rejected because the current oversized service is already difficult to maintain; decomposition is an active architecture requirement.

## Consequences

- Positive: the UI and Fuel observe one project truth and one capacity signal; fast work dispatches without an extra trigger; retries are safe after the runtime has acknowledged durable admission.
- Positive: one operation vocabulary applies to component and canvas work, while exact target/snapshot evidence preserves reproducibility.
- Positive: I28 makes the future `canvas.toml` and project layout accountable to the same replay rule; no UI-only target or generated tool file can silently change the result.
- Positive: geometry can use GDSFactory directly without duplicating its core API; generated artifacts still pass through engine ownership.
- Negative: implementing the contract requires a shared runtime lifecycle, durable scheduler/ledger recovery, capacity events, public scope-aware operations, and cross-route session policy enforcement.
- Negative: the current engine is not yet compliant: `src/project/service.py` is about 3,809 lines and `src/composition.py` about 2,585. Split the project service first and avoid growing composition toward the limit.
- Evidence required before claiming readiness: exercise frontend and MCP against one runtime; restart after acknowledged queued work; saturate and release capacity with both clients; verify coalescing across adapters on identical snapshots; target unit and canvas operations; author layer geometry and inspect provenance; confirm repair accounting across all solver routes.
