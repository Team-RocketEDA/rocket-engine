## Summary

The PRD already establishes useful foundations: the engine owns project behavior, MCP and UI share operation semantics, components can link schematic/layout/model views, Python can access prepared GDSFactory, and the harness defines a design-change repair cycle. It did not consistently specify one runtime, durable admission, capacity signaling, universal target scope or the current implementation boundary. Some adjacent passages contradicted the target by permitting per-module process sharing, expecting separate calls to create separate runs, and requiring `run_job` after submit.

The older E2E review demonstrates selected journeys and current source behavior, not the full ubiquitous-engine vision. Several map entries marked proven are only partial when read as public adapter guarantees. I27 completion reporting is wired in the reviewed source now, so the old map's “unproven” conclusion is stale. The detailed current comparison is below.

## E2E readiness context

The rereview is useful evidence of product slices, but it does not establish full engine readiness:

- Analog post-layout remains blocked by real flow gaps: device model availability, DRC findings, GDS extraction and LVS mismatches. The related `POSTLAYOUT-REAL`, `DRC-BANDGAP-TRIAGE`, `EXTRACT-GDS` and `LVS-BANDGAP-TRIAGE` tickets remain Ready.
- The mixed-signal journey has a passing sigma-delta co-simulation slice but outstanding top-level DRC/LVS triage (`MIXED-TOP-TRIAGE`).
- Digital adapter and hermetic qualification are green, but live flow readiness depends on a pinned LibreLane/tool distribution and compatible PDK root; the ticket's “hollow entrypoint” wording is stale against the report.
- Photonic circuit simulation and view synchronization have useful coverage. Missing GDSFactory in one environment and the earlier MEOW stdout behavior are environment/source-snapshot findings, not proof that public layer geometry is complete.
- Magic's source confirms that a usable bundled SCMOS profile can support drawing without a foundry PDK, but its core does not provide a universal material palette; its empty `minimum` fallback is not drawable. The user later withdrew RocketEDA's no-PDK/default-palette requirement. The tutorials now ground the layout workflow; the source confirms that overlap, contacts, connectivity, grid/rules and CIF/GDS transforms belong to technology semantics, not just visual layer names.
- The [Magic layout-editor workflow blueprint](../../../../PRD/tools-research/magic-layout-editor-workflows.md) translates tutorials 1–11 into product tasks. Magic informs the physical layout editor only; it does not replace the separate KiCad/Xschem basis for schematic and symbol editors.
- The sprint board's completed `LAYER-SERVING` ticket serves PDK stackup/viewer rows/presets and 3D heights. It does not implement an editable layer catalog or layout editor. New editor tickets track that missing capability separately.
- The board also has ready work for MCP contract/schema, batch parallelism, project/entity CAS and workflow coverage. These enable the architecture but do not substitute for one-runtime integration or durable queue recovery.

## PRD amendments made

- `PRD/README.md`: states the KiCad-like ASIC product destination, full editor direction, and versioned TOML `canvas.cst` design-intent flow.
- `PRD/tech-stack.md`: mandates one EngineRuntime, shared state across frontend/MCP transports, durable recovery, the module-size rule and YAML/TOML division.
- `PRD/tools-research/frontend-tooling-spec.md`: aligns coalescing, scope, durable admission, immediate dispatch, capacity pause/resume and current implementation status; defines I28 ingredients and result-level replay.
- `PRD/tools-research/tooling-operations.yaml`: removes the false “implemented two-phase” claim; generic `run_job` is a one-call submission, not a second trigger.
- `PRD/tools-research/suggested-api.md`: defines unit/canvas target closure, layer-aware geometry, and TOML `canvas.cst` as versioned source alongside YAML records.
- `PRD/tools-research/behavior-invariants.yaml`: binds I28 to the project revision including `canvas.cst` and its contained references; adds I34–I38. New invariants remain planned and `not_run`.
- `PRD/tools-research/magic-vlsi-source-dissection.md`: records the source-level Magic methodology and separates verified behavior from RocketEDA design choices.
- `PRD/tools-research/magic-layout-editor-workflows.md`: maps Magic tutorial workflows to RocketEDA product and engine capabilities.
- `rocket-engine/docs/adr/013-magic-aligned-technology-driven-layout.md`: supersedes ADR-012's no-PDK/default-palette clauses while retaining first-class editor, I28 and client-neutral operation requirements.
- `PRD/tools-research/frontend-requirements.md`: makes layout editing first-class and resolves paintable layers through an explicit technology profile.
- `PRD/README.md` and `PRD/tools-research/behavior-invariants.yaml`: replace the withdrawn no-PDK drawing promise with an explicit technology-profile requirement; I37 remains planned and `not_run`.
- `PRD/harness/README.md`: migrates design targets to `canvas.cst`, keeps the repair budget harness-side, counts parallel checks once per changed design, and closes alternate solver-route bypasses.
- `rocket-engine/AGENTS.md` and ADR-011: make I28 and the module-size ceiling standing engine rules.
